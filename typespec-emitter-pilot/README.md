# TypeSpec emitter pilot — generated artifacts (end-to-end demo)

This folder is **not production code**. It is a drop-in copy of the output produced by an
internal pilot/prototype TypeSpec emitter
(`@azure-tools/typespec-azurite-emitter-pilot`, built in `Azure/typespec-azure`) against a small
"Queue-like" TypeSpec fixture, placed here so it can be exercised with Azurite's own TypeScript
toolchain (`tsc`, `ts-node`, `mocha`) as evidence that a TypeSpec-generated artifact set is
structurally consumable by Azurite's runtime conventions — without requiring any changes to
Azurite's real `src/queue/generated/**` artifacts in this PR.

See the companion pull request: **Azure/typespec-azure#5614** ("Pilot: Azurite emitter prototype
on emitter-framework-style architecture") for the emitter source, its own unit/e2e tests, and a
detailed README covering design decisions and scope.

## What's here

- `fixture/base.tsp` — a toy TypeSpec service (not real Azure Storage) with three operations
  representative of Storage's shape: a PUT with a JSON body, a GET with a custom response header,
  and a GET with query-string parameters.
- `fixture/azurite.tsp` — an `azurite.tsp`-style overlay applying emulator-specific documentation
  augments on top of `base.tsp`, demonstrating the overlay pattern central to the real migration
  design (base Storage TypeSpec stays unchanged; Azurite-specific behavior layers on top).
- `generated/models.ts`, `generated/operations.ts`, `generated/handlers.ts` — the **unmodified,
  copy-pasted output** of running the pilot emitter against the fixture above. These were
  generated by `tsp compile` via the emitter in `Azure/typespec-azure`'s
  `packages/typespec-azurite-emitter-pilot`; nothing in this folder was hand-written.
- `../tests/typespec-emitter-pilot/generatedArtifacts.test.ts` — a Mocha test (tagged `@loki` so
  it runs under Azurite's existing `npm test` / `npm run test:in-memory` scripts, no server or
  storage backend required) that imports these generated files directly and asserts the
  structural elements Azurite's real dispatcher/handler boundary relies on are present and
  correctly shaped — mirroring the comparisons already made against this repo's
  `src/queue/generated/{handlers/IQueueHandler.ts,middleware/dispatch.middleware.ts,
  artifacts/{parameters,specifications}.ts,Context.ts}` in the companion PR.

## What this proves

- The generated TypeScript **compiles cleanly** under Azurite's own `tsconfig`/`ts-node` setup
  (no pilot-specific build tooling involved).
- The generated route/operation metadata carries the fields a dispatcher modeled on
  `dispatch.middleware.ts`'s `isRequestAgainstOperation` would need: HTTP method, path template,
  and per-parameter `{wireName, location, required}`.
- The generated handler interface's method shape — `(params, context) => Promise<Response>` —
  matches the calling convention of Azurite's real `I*Handler` interfaces.

## What this does **not** prove / explicitly out of scope

- This does **not** wire the generated handler interface into Azurite's real Express
  middleware/dispatch pipeline, nor replace any file under `src/queue/generated/**`. Doing that
  is follow-on work for a real collaboration, not this pilot.
- No XML/OData/streaming/Table-specific behavior is modeled — the fixture is a minimal toy slice,
  not real Azure Storage Queue/Blob/Table.
- No attempt was made to match Azurite's exact `msRest` mapper/serializer format
  (`parameters.ts`/`specifications.ts`); the pilot's metadata shape is deliberately simpler and
  emitter-native rather than a byte-for-byte clone of the AutoRest-generated format.

This PR is intended purely to let the Azurite team run/inspect pilot-generated code inside their
own toolchain and give feedback, ahead of any decision to invest further in this direction. It is
**not intended to be merged as-is**.
